# Agent Notes

## Project shape

- This is a single Leiningen/Clojure library (`net.clojars.macielti/health-check`), not a workspace or runnable application. The implementation is under `src/health_check/component.clj`, in the `health-check.component` namespace; `project.clj` sets that namespace as the REPL init namespace.
- Treat `project.clj` as the canonical build and dependency manifest. `pom.xml` is generated by Leiningen and ignored by Git; edit `project.clj`, not `pom.xml`.
- Run Leiningen commands from the repository root. The project uses Clojure 1.12.6 and Integrant 1.0.1.
- The implementation is an Integrant component. Its `::health-check` init/halt methods expect `components` to be a map and `to-be-checked` to be a set; only selected components' `health-check-fn` values are invoked.
- The current main revision has a tracked scaffold at `test/health_check/core_test.clj`, while the configured `test/unit`, `test/integration`, and `test/helpers` directories are empty or untracked. Keep new tests in the configured paths so the dev profile can discover them.
- `README.md`, `doc/intro.md`, and `CHANGELOG.md` still contain template/FIXME material. Use `project.clj`, the source, and tests as the current sources of truth.

## Code conventions

- Use `defn` for ordinary helpers, `defn-` or `^:private` for implementation-only helpers, and `s/defn` when a function has explicit Schema input/return annotations, as in `health_check.component`.
- Prefer destructuring for map-shaped arguments. Keep the whole request/context with `:as` when it is needed; use `[_ {:keys [...] }]` for Integrant lifecycle methods.
- For nested request contexts, destructure the relevant request keys and retain the whole context with `:as` only when it is needed, for example `[{{:keys [json-params]} :request :as context}]`.
- Keep dependent bindings in one `let`; avoid nested `let` forms when the values are related. Use persistent map literals instead of `array-map`, and keep scalar arguments named/typed instead of wrapping them in a map solely for destructuring.
- Use `_` for unused Integrant lifecycle arguments and underscore-prefixed names for intentionally unused values.

## Integration tests

- Put integration tests under `test/integration/`; `project.clj` includes that directory in `:test-paths`, and `lein test` runs it with the unit tests. There is no separate integration task or selector.
- Define a `system-components` map with namespaced Integrant keys and `ig/ref` dependencies where the graph needs them. Use the component key `::component/health-check` (that is, `:health-check.component/health-check`) and supply `:components` and `:to-be-checked`.
- Initialize the graph with `(ig/init system-components)`, exercise the initialized component, and call `(ig/halt! system)` in a `finally` block. Integration here means exercising Integrant wiring; it does not require an external process or service.
- Use `s/deftest` and `matcher-combinators.test/match?` for new tests where appropriate. `.lsp/config.edn` maps `schema.test/deftest` to `clojure.test/deftest`.

## Development and verification

- Use Leiningen; run `lein deps` before verification. `lein check` is the source compile/check command.
- `lein test` uses the `:dev` test-path replacement. On the current main revision those paths are empty, so the command can report 0 tests; do not treat that as meaningful coverage. The checked-in `test/health_check/core_test.clj` is a stale scaffold whose test intentionally asserts `(= 0 1)` and currently fails.
- To run the checked-in scaffold directly, bypass the dev profile with `lein with-profile -dev test`; run one var with `lein with-profile -dev test :only health-check.core-test/a-test`. Replace the scaffold with real regression tests rather than treating its failure as a signal.
- Run focused tests for new namespaces with `lein test <namespace>` and a single var with `lein test :only <namespace>/<var>`.
- `lein lint` runs the configured `clean-ns` → `format` → `diagnostics` checks. `lein lint-fix` runs non-dry namespace cleanup and formatting, but not diagnostics; use it only when those changes are in scope, inspect the diff, and rerun `lein lint`.
- On the current main revision, `lein lint` fails in `clean-ns` because the requires in `src/health_check/component.clj` are not sorted, and diagnostics can report pre-existing unused bindings/public vars or unresolved symbols. Distinguish those baseline issues from regressions in the change under review.
- `lein repl` starts in `health-check.component`. Use `lein antq` only for intentional dependency updates, then review `project.clj` and rerun verification.
- There is no tracked CI, pre-commit, codegen, migration, or deployment configuration; use the local commands above as the verification baseline.

## Gotchas

- The `:dev` profile replaces `resources` with `test/resources`; account for that when loading configuration fixtures.
- Schema is `1.4.1` in the base dependencies but `1.4.2` in `:dev`; test results can therefore differ from the library's published dependency set.
- The configured test paths and the stale test namespace/file need to be aligned with the `component` implementation before relying on lint or test output.
- Verify APIs against the source and `project.clj` rather than copying template documentation.
